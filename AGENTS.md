# Image Compressor — инженерный вход

Локальная утилита для пакетного сжатия и преобразования изображений. Ценность — получить читаемый результат с предсказуемыми параметрами, не потеряв исходники и прежние результаты. Входы: JPEG, PNG, WebP, HEIF/HEIC, AVIF; выходы: JPEG, WebP, HEIF/HEIC, AVIF (PNG только вход). Доступность кодека проверяется фактически, не по наличию имени в списке. Принятый прикладной контракт — [Application API v1](docs/architecture/application-api.md); авторские проверки, независимый ACCEPT после ремонта R1/R2 и точные ограничения — в [verification](docs/verification/command-first-refactoring.md). Это не EXE-релиз и не квалификация всех платформ.

## Архитектурный курс и границы

- Сначала независимый прикладной API: команды/запросы, типизированные результаты и ошибки, единый владелец правил и файловых эффектов. CLI, GUI и MCP — адаптеры, не отдельные реализации компрессора.
- Ядро не импортирует Qt, CLI-парсер или MCP SDK, не вызывает `input()`, не печатает диагностические сообщения в машинный stdout. Прямой вызов API должен работать без окна.
- Выбирать минимально достаточную архитектуру по реальным гарантиям. Очередь, daemon, IPC, Command Bus, БД, workflow и MCP заранее не требуются. Oracle обосновывает профиль и границы.
- Command-first-срез и отдельный [FigCraft → PySide6 эксперимент](docs/figcraft_gui_experiment/REPORT.md) независимо приняты в своих границах. Настоящий дизайн в `design/` и `gui_pyside6_v2/` сохранены поверх неизменённого публичного API; **канонический GUI продукта — `gui_pyside6_v2/`**; принятый локальный EXE — `candidate-05`, а `candidate-03`/`candidate-04` — `superseded` и убраны в Recycle Bin, а историческая PyQt6-оболочка `gui/`/`gui_main.py` и compatibility facade удалены из рабочей копии в legacy-retirement 2026-10-28 (история сохранена в Git) ([release record](docs/releases/windows-pyside6-20261028-candidate-04.md)). Ядро и PFK snapshot не менять; PySide и PyQt проверять в отдельных средах/процессах (PyQt в рабочем наборе больше не поставляется). MCP-сервер продукта не входит; deletion — только opt-in (см. ниже). Технический/визуальный ACCEPT не квалифицирует все платформы, DPI или физические OS-dialog/drop; новые изменения требуют отдельного поручения.
- Standalone Windows x64 EXE принятого PySide6 GUI независимо принят в отдельной [exact-byte технической и визуальной границе](docs/figcraft_gui_experiment/05-windows-exe-verification.md). [Выпущенный план](docs/figcraft_gui_experiment/04-windows-exe-plan.md) сохраняет исходные discovery/NOT RUN, прежний source-GUI ACCEPT не переименовывается во frozen proof. Реализованы `tools/windows_exe/`, `tests_windows_exe/` и EXE guide/verification; core, оба GUI, прежние tests, design, pyproject, legacy spec/bat и PFK неизменны. Build toolchain принадлежит только `.agent-work/windows-exe/build-venv`; старые среды/outputs не заменять. Artifact локальный и неподписанный, без чистой-machine/всех платформ/signing/release qualification; бинарники не публиковать. Закрытый follow-up не продолжать без нового поручения. Принятый `candidate-03` остаётся fallback. Текущая proposed-сборка `candidate-04` собирается из HEAD `43554f8` + bounded deletion/journal delta через detached worktree/junction и существующий build-venv; её build-id, байты/SHA, overlay и статус — в [release record](docs/releases/windows-pyside6-20261028-candidate-04.md). EXE обязан содержать `image_compressor._windows_deletion`, 13 `control-*.svg` + `tokens.json`, не содержать PyQt6/legacy. Артефакт не пересобирать и не подменять: новый бинарник — новый build-id, собственный build и новый независимый exact-byte ACCEPT; `.lnk`/launcher обновляет Reviewer только после ACCEPT.
- Удаление исходников — **opt-in**: `delete_original` строго bool, default OFF; видимая галочка в canonical GUI кликабельна (клик по индикатору/подписи или Space), включение = согласие, отдельного modal/повторного подтверждения нет. Исходник удаляется безвозвратно только после verified final output, flush и повторной source-проверки, на supported Windows local fixed NTFS; failure/cancel/unknown не выдаются за deleted и не удаляют до destructive point; unsupported — явная ошибка, не тихий False. Корзины/undo нет. Проверки/квалификация — только synthetic disposable files, никогда личные/проектные. Функция входит в принятый `candidate-05`; `candidate-03` её не содержал; контракт — [Application API](docs/architecture/application-api.md), план — [gui-feedback](docs/plans/gui-feedback-source-deletion.md).
- Только create-only публикация проверенного staging через atomic no-replace hard link с final readback; сохранять исходники и прежние результаты. При `delete_original=True` исходник удаляется только после verified final output и только на supported Windows local fixed NTFS; при `False` он сохраняется и это явно отражено в `source_disposition`/`counts.deleted`. Тихий False, удаление до проверки или выдача unknown за success запрещены. Общий контракт и tests владеют коллизиями/кооперативной отменой; trusted local namespace не означает sandbox или crash durability.
- Журнал GUI в существующем нижнем блоке: вкладка «Журнал операции» — **только** человеческая summary из typed `ItemResult`+verified artifact (имя/формат, было→стало, меньше/больше/unknown, статус, удалён/сохранён/unknown), без raw events и путей. Вся техническая информация — в соседней существующей вкладке «Подробности»: raw `event=`, локальные пути, params, elapsed, SHA-256, errors, dispositions; read-only, selection/Ctrl+C. Второй technical-контейнер/кнопку/вкладку не создавать; в diagnostics/`Controller.log_line` пути не протаскивать. Per-file время не выдумывать; operation elapsed — только реально измеренный GUI snapshot. Ограничения (500 blocks / 50 items) — честные, не долговечный audit log.

## Рабочий цикл и команда

1. Проверить корень, ветку, фактические изменения; найти владельца и потребителей символа. Сохранить чужую работу. До существенной записи определить область и наблюдаемые критерии.
2. Oracle планирует → Coder реализует и проверяет → независимый Reviewer принимает. Hermes после оформления основы — тонкий оркестратор, не второй разработчик/проверяющий.
3. Роли Pi раздельны: [oracle](.pi/agents/oracle.md) — `openai-codex/gpt-6-astra`, `xhigh`; [coder](.pi/agents/coder.md) и [reviewer](.pi/agents/reviewer.md) — `openai-codex/gpt-6.1-sol`, `max`. Сохранять отдельные беседы; замечания возвращать тому же автору, проблемы архитектуры — тому же Oracle. Нельзя молча менять модель/поставщика. Реально наблюдённый уровень рассуждения отличать от запрошенного.
4. Один писатель на пересекающиеся файлы. До ACCEPT кандидат и index заморожены; Reviewer пишет только свой отчёт/probes, не исправляет проверяемый код. После ACCEPT тот же Reviewer завершает затронутые docs/instructions и разрешённое selective сохранение/доставку по [рабочему циклу](docs/instructions/development.md). Новая source/test неисправность возвращается тому же Coder; closeout не новая независимая приёмка. Один связный обзор, без проверяющего проверяющего.
5. Существенные решения, запуски и отказы кратко фиксировать в [LOG.md](LOG.md); локальные сырые сессии/результаты — в игнорируемом `.agent-work/`. Долговечное знание принадлежит `docs/`, не только чату.
6. До завершения обновить относящиеся контракты, архитектуру, команды/примеры и ограничения; проверки должны пройти через настоящий вход с повторным открытием результата. План, написанный тест, exit процесса и независимое принятие — разные факты.

## Полномочия и сохранность

Разрешены чтение/изменение этого проекта, создание отдельных веток, изолированные зависимости разработки и тесты на синтетических данных в пределах поручения. Не читать `.env`, credentials, личные изображения/архивы, чужие журналы/БД. Не менять глобальные настройки Pi/Hermes или другие проекты. `tools/project-foundation/` — полная сохранённая редакция пакета; не редактировать её при обычной разработке. Репозиторий-источник пакета также только для чтения.

Ветки этой работы: `docs/project-foundation` для подготовки, затем `refactor/command-first` для реализации; фактические ref'ы, хеши артефактов и граница принятого состояния — в [release record](docs/releases/windows-pyside6-20261028-candidate-05.md). Основа перешла как незакоммиченные изменения, не отдельный docs-коммит. `develop`/`docs/project-foundation` — предки канона, `main` — старая расходящаяся линия; чужие ref'ы не мержить, не переименовывать, не удалять и не пушить. По прямому поручению пользователя accepting Reviewer после ACCEPT владеет docs closeout, selective stage/commit принятого среза и branch-only push в существующий `origin` этого проекта на `refs/heads/refactor/command-first` с exact SHA readback. Coder/Oracle index/commit/push не получают; новых разрешений перед каждым принятым срезом не требуется. Merge/tag/release/force/переписывание истории, новый remote и изменение visibility не разрешены. Не применять `reset`, `clean`, `stash`, массовый `add` или обход защит ради чистого дерева; private outputs/sessions/venvs/cache/build/dist не публиковать.

Канонический запуск GUI: отдельная PySide-среда `.agent-work/figcraft-gui-experiment/pyside6-venv` + `python -m gui_pyside6_v2`; bare install — только Pillow. Тесты: core `.venv` (`pytest tests`, ruff/mypy) и offscreen PySide suite, packaging/EXE — `tests_windows_exe` с explicit `IC_FROZEN_EXE`. Сборка EXE — только существующий `.agent-work/windows-exe/build-venv` по [WINDOWS_EXE](docs/figcraft_gui_experiment/WINDOWS_EXE.md); без installs/downloads. Фактическая исходная среда и правила запуска — в [тестировании](docs/instructions/testing.md). Непроверенные новые команды нельзя называть работающими. Итог — полезное изменение, настоящие проверки/NOT RUN, ветка/сохранение и конкретный обязательный остаток. Когда исходная цель выполнена, остановиться.
