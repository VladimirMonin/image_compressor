# Изменение диагностики

Основание и единый владелец политики — [наблюдаемость](../foundation/observability-policy.md); проверка — [тестирование](testing.md). Применимый producer — прикладной владелец операции. CLI и Qt-адаптеры отображают факты. Новый PySide6 controller также сообщает закрытые события discovery/lifecycle; исход преобразования остаётся у API. Новый реестр/trace framework не вводить без требования.

1. От сценария выбрать факт: начало, результат, существенный отказ/skip или cleanup. Различать запрос, начало, опубликованный файл, удаление и завершение; не писать «успех» до проверки результата. Связать событие с текущей операцией/элементом, если нужна корреляция, а не читать позднее глобальное mutable-состояние.
2. Явно выбрать поля и источник: стабильный event/reason/outcome, индекс элемента, формат/качество, пиксели, counts, байты, длительность с единицей. Настоящий ноль — `0`, неизвестное — omitted/null по контракту. Не логировать произвольный объект/DTO или `repr(exception)`.
3. Не включать пользовательское содержимое изображения/EXIF, полный путь/имя личного файла, домашний каталог, credentials/env и произвольный текст exception/cause. Нельзя обойти запрет через debug print, stderr, UI/export или raw fallback. Безопасные соседние counts/reason сохраняются независимо от отброшенного поля.
4. Использовать стандартный достаточный logging-путь. Ядро не настраивает глобальный root logger, не вызывает `basicConfig` при импорте, не печатает в stdout. CLI машинного режима пишет единственный предусмотренный ответ в stdout; диагностику — отдельно. Структурированный результат может содержать нужные локальные ссылки на явно выбранные файлы по своему контракту, но не копируется целиком в технический журнал.
5. Не писать каждый tick; обязательные исходы не терять за sampling. Ошибка handler-а не должна повторно запускать преобразование, подменять исход операции или писать raw data после отказа безопасного пути. Постоянный runtime log по умолчанию не нужен; при его добавлении сначала определить cap/ротацию/число копий/cleanup и поведение при I/O failure. Нереализованное хранение так и обозначить.
6. До запуска обеспечить собственный sink и синтетические данные. Проверить emitter → выбор/фильтрация → formatter → handler → flush/drain → actual bytes. В них должны быть нужные event/identity/count/reason **и** отсутствовать forbidden sentinels из синтетического пути/исключения. Пустой файл, disabled logger и один `caplog` не доказывают privacy настоящего sink.
7. Проверить затронутые consumer-ы отдельно: JSON stdout реально разбирается и соответствует фактам продукта; stderr не загрязняет stdout; изменённый Qt-buffer/export не получает непроверенную raw-ветку. Не делать ложное заявление о приватности неизменённого старого UI.
8. Зафиксировать exact command, raw exit, наблюдение/подмены и ограничения. Обновить политику/контракт при изменении канала, полей, единиц, privacy-chain или хранения. Повторить affected проверки после изменения formatter/handler, не весь проект ради одного безопасного count.

## Права и завершение

DEBUG — подробность, не новое право на содержимое. DEV-content/support export не реализованы и не разрешены автоматически. Локальное отображение, постоянное хранение, экспорт и внешняя отправка — разные действия. Скрытой аналитики нет; новая передача требует решения владельца о получателе/цели/категориях/включении/хранении. Использование облачных Pi-агентов не разрешает телеметрию продукта.

## Журнал GUI: два уровня

Вкладка «Журнал операции» — только человеческая summary из typed `ItemResult`/verified `Artifact`: имя/переход формата, было→стало, меньше/больше/unknown, статус (running/succeeded/failed/cancelled/partial и deleted/retained/unknown), без выдуманного per-file времени и без raw events/путей; operation elapsed — только реально измеренный GUI snapshot, иначе «—». Все технические детали — в существующей вкладке «Подробности»: прежние `event=` строки, локальные пути, params, SHA, errors, dispositions; read-only, selection/Ctrl+C, raw-буфер 500. Отдельного вложенного technical-toggle/контейнера нет. Пути в `Controller.log_line`/diagnostics не протаскиваются. 500 blocks/50 items — честные пределы представления, не persistent audit trail; Clear/закрытие окна снимают журнал. Статус передаётся текстом, не только цветом.

`LOG.md` хранит короткие события разработки без личного содержимого; сырые model sessions/tool outputs туда не вставлять. Проверка достаточна, когда полезные факты реально дошли, запреты проверены и предел вывода честно указан. Статическая проверка Markdown — не runtime privacy PASS. Независимый Reviewer проверяет связный результат по [рабочему циклу](development.md). Для нового PySide6 канала отдельная приёмка непустого буфера и отсутствия synthetic path/postfix/exception sentinels зафиксирована в [REPORT](../figcraft_gui_experiment/REPORT.md); она не расширяет privacy-гарантию неизменённого старого UI.
