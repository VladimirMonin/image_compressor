# Рабочий цикл

Область — только `image_compressor` и разрешённые локальные результаты этой работы. Основа: [AGENTS](../../AGENTS.md), [философия](../foundation/project-philosophy.md), [архитектурные принципы](../foundation/architecture-principles.md). Эта инструкция не даёт прав на личные данные, публикацию, глобальную настройку инструментов или соседние проекты.

1. Проверить `git status --short --branch`, текущую ветку и фактическую базу. Прочитать определение и реальных потребителей изменяемого символа; не угадывать существование модуля, зависимости или команды. До записи определить нужную область/сохраняемое/критерии; пакет `tools/project-foundation/` не редактировать.
2. Для существенного изменения сформулировать наблюдаемый результат, важные ошибки и сохранность. Использовать [pf-plan](../../tools/project-foundation/skills/pf-plan/SKILL.md) и для независимого API — [pf-command-first](../../tools/project-foundation/skills/pf-command-first/SKILL.md). Малое исправление не требует нового ADR/исследования.
3. Oracle читает настоящие исходники и нужные первичные разделы, выбирает минимальный профиль и пишет исполнимый план с контрактом и срезами. Новые имена/сигнатуры до реализации помечаются как целевые. План не подтверждает готовность кода.
4. После завершения плана создать отдельную ветку `refactor/command-first`. Coder реализует связный срез, включая необходимые тесты, совместимость и документацию. Один писатель на общие DTO/API/файлы. Не брать дизайн GUI, новую оболочку MCP и соседнюю уборку.
5. Проверить настоящий вход и результат по [тестированию](testing.md); диагностический вывод — по [логированию](logging.md). Первую ошибку сохранить и классифицировать. Не ослаблять assertion/guard ради зелёного результата. Необязательное улучшение не превращать в новый этап.
6. При существенной неопределённости или повторном отсутствии продвижения обращаться к тому же Oracle: исходное требование, точные источники, фактическая ошибка/результат и конкретный вопрос. Обычное исправление теста или опечатки не требует ещё одного Oracle.
7. До передачи обновить действительный контракт, карту архитектуры, инструкции и README с настоящими командами. Самоотчёт/локальный статус не заменяют знание у владельца. Ненужное изменение документа не делать, no-impact объяснить кратко.
8. Coder замораживает кандидат и передаёт actual changed paths, проверки/raw exits, остаток и локатор своей сохранённой Pi-беседы. Reviewer в отдельной беседе проверяет всю заказанную границу и существенные риски; не принимает авторский PASS как собственную проверку. Обязательные file:line замечания возвращаются тому же кодеру, затем исправленный кандидат — тому же Reviewer. Нет проверяющего проверяющего.
9. После ACCEPT тот же Reviewer завершает затронутые публичные docs/instructions, затем проверяет свою closeout delta и выполняет разрешённые selective commit/push ниже. Source/tests/manifest не чинит: новый code finding возвращается Coder. Closeout author verification не называть ещё одним независимым review; достаточные неизменённые checks переиспользовать. Перед обновлением текущего отчёта сохранить его исходные байты в свежем reviewer root.
10. Передать один короткий итог: полезный результат, фактические проверки и NOT RUN, docs completion, полный local commit, destination/ref и прочитанный remote SHA либо точный blocker. Когда весь заказанный результат выполнен — остановиться.

## Pi и полномочия ролей

Профили: [Oracle](../../.pi/agents/oracle.md), [Coder](../../.pi/agents/coder.md), [Reviewer](../../.pi/agents/reviewer.md). Для этой задачи Oracle — Codex Astra xhigh, Coder и независимый Reviewer — Codex Sol 6.1 max. Hermes лично готовит основу, затем координирует; реализация и содержательная техническая проверка принадлежат Pi. Флаги запуска, native model/thinking events и ответ модели фиксируются раздельно. Запрошенный max нельзя молча заменить другой моделью или меньшим поддерживаемым уровнем.

Каждая роль получает отдельную сохраняемую беседу. Исправления продолжают тот же session file после завершения прежнего процесса. Один локальный `.agent-work/coordination.json` хранит актуального владельца/процесс/путь handoff; подробные сырые результаты не дублируются во всех отчётах. Использовать доступные codebase-memory, Serena и ast-grep при конкретной пользе; отсутствие этих необязательных средств не разрешает устанавливать новые пакеты или блокировать достаточный поиск штатными read/grep.

## Ветки, Git и документация

Подготовка — `docs/project-foundation`; после плана — `refactor/command-first`. Не перезаписывать существующую ветку при коллизии имени. Незакоммиченные документы допустимо перенести в ветку рефакторинга, явно сообщив отсутствие сохранённого docs-коммита.

Первоначальный запрет Git writes относился к подготовке/реализации и read-only review. Последующее прямое поручение пользователя отдельно разрешает **тому же accepting Reviewer после ACCEPT** docs/instructions closeout, selective stage/commit принятого coherent slice и push feature branch. Эта инструкция синхронизирует данное решение; она не выдаёт новые права Coder/Oracle и не требует повторять разрешение перед каждым принятым срезом. Основание принятия и пределы — [verification](../verification/command-first-refactoring.md).

Reviewer — единственный index writer этой стадии. До записи сверить branch/base, accepted source/test hashes и actual modified/untracked path set; оставить только свою необходимую docs delta поверх принятого состава. Stage только явные принятые paths, включая авторизованную foundation; просмотреть весь staged diff, проверить каждый blob и сохранность raw vendored originals по UPSTREAM, не только рабочие hashes. Исключить `.agent-work`, sessions/private outputs, venv/cache/build/dist. Commit в стиле существующей истории (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`); проверить actual parent/branch/path set/blobs и остаток index/worktree. Если README/package input изменён closeout-ом, выполнить affected final-byte package check; неизменённый полный suite не повторять без причины.

Доставка разрешена только в существующий `origin` проекта на `refs/heads/refactor/command-first`. Проверить remote и весь outgoing range, включая уже существовавший base commit; не выдавать его за новый. Установить применимые CI gates из действующих правил/реальных branch rules, отсутствие checks не называть green CI. Отправлять frozen полный SHA явным refspec: `git -c push.followTags=false push origin ACCEPTED_SHA:refs/heads/refactor/command-first`, затем exact ref/SHA readback через `git ls-remote` (при bounded failure — существующий authenticated gh API). Не повторять push лишь из-за недоступного readback. Пользоваться существующей native auth, не читать credentials и не менять persistent helpers/config. Push-only blocker не отменяет принятую реализацию/локальный commit.

Не применять `reset`, `clean`, `stash`, `restore`, массовый `add`, обход hooks или переписывание истории. Force/merge/tag/release/visibility changes и новый remote/репозиторий не разрешены. На новой source/test неисправности остановить сохранение неподходящего кандидата и вернуть finding тому же Coder; второго review-контура не создавать.

Долговечные новые документы используют [metadata пакета](../../tools/project-foundation/references/metadata.md), native AGENTS/профили/сырые сессии — собственный формат. Относительные ссылки считаются от конечного документа. Не создавать два редактируемых канона одного правила; пакетные шаблоны не заменяют проектную адаптацию. Статус документа и выполненность функции различаются.
