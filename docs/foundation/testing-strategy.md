# Что должны доказывать тесты

Тест обнаруживает неправильный результат пользователя, а не подтверждает число вызванных методов. Главные недопустимые потери — порча исходника, затирание прежнего результата, ошибочное удаление, ложный успех и потеря существенной ошибки в пакете.

## Границы

- Проверки правил: параметры, поддерживаемые расширения/форматы, размеры с сохранением пропорций и без увеличения, выходные имена и конфликты.
- Интеграция: настоящий прикладной API, Pillow и доступные кодеки, временная файловая система; файл повторно открывается и проверяются формат/размер/существенные свойства.
- CLI-сценарий: настоящий подпроцесс и разбор аргументов → тот же API → реальный файл, JSON stdout и код завершения. CLI не подменяется вызовом тестового helper-а.
- Совместимость: настоящий сохранившийся `ImageCompressor`/worker → общий API. Окно и визуальный дизайн не предмет этого этапа; Qt при необходимости проверяется без экрана в отдельной границе.
- Статические проверки: import-зависимости и отсутствие Qt/терминального ввода в ядре, Ruff и типы по затронутой области. Они не заменяют обработку изображения.

## Выбор по риску

Для рефакторинга общего пути необходим связный набор: успешная одиночная и пакетная обработка, каталог/подкаталоги, дубликаты, одинаковые расширения и коллизии, некорректные параметры/путь/данные/недоступный кодек, частичный итог, применимая отмена и следующая операция. Конкретные критерии и поддерживаемые гарантии определяет план Oracle; не строить бессмысленное произведение всех параметров.

Публикация и удаление требуют различимых исходных байтов, readback и отказов до/после точки эффекта. Подмена сбоя записи или контролируемый callback полезны; подмена прикладного владельца заранее успешным результатом — нет. Не «исправлять» ожидание под случайное небезопасное поведение.

## Изоляция и инструменты

До collection/import проверить конфигурацию и ранние эффекты. Тестовые изображения создаются программно в `tmp_path`/собственном временном каталоге, не берутся из личных папок. Разработческие скрипты — в `tests/` или `.agent-work/`, не в корне. Процессы и файловые дескрипторы получают cleanup сразу после создания, в том числе при частично неудачном setup. Удаляются только собственные артефакты.

Исходно автоматический набор не настроен, в `.venv` нет pytest/Ruff/mypy. `test_gui.py` — ручной устаревший launcher, не пройденный тест. Фактические команды и их состояние принадлежат [инструкции тестирования](../instructions/testing.md), а не копируются сюда как второй реестр.

Зависимости разработки ставятся только в окружение проекта; глобальный Python/Pi не изменять. Для проверки Markdown используется только собственная project-local `.agent-work/foundation-venv` с PyYAML 6.0.3 и явным corpus; окружение соседнего source-проекта не используется. PyYAML не добавляется в runtime компрессора ради документов.

## Диагностика и итог

Проверки диагностики проходят настоящий formatter/handler, flush и чтение байтов: разрешённые события/числа есть, запрещённые синтетические sentinels отсутствуют. `caplog` или пустой выход не доказывает постоянное хранение. Машинный ответ CLI и диагностический журнал — разные каналы; политика каждого явна.

Автор фиксирует команды, выборку, raw exit, реальные компоненты/подмены, skips и предел. Написано, выполнено, пропущено и независимо принято не смешиваются. Первая ошибка сохраняется с причиной; ошибочный тест и дефект продукта различаются. Неизменённые проверки используются повторно по применимости, изменённый контракт/fixture требует адресного повторения.

Один независимый Reviewer решает достаточность готового кандидата; обязательные замечания возвращаются тому же кодеру. Нет второго контура проверки ради красивой отчётности. Завершение — все заказанные критерии выполнены, ограничения честно названы; новый GUI, MCP и выпуск EXE не объявляются проверенными.
